# Architecture Decision Records

## 철학
학습 프로젝트 규모에 맞게 **단순한 구현을 우선**한다. 다만 **외부 API 과금 보호는 타협하지 않는다.**
드문 엣지 케이스는 복잡한 장치로 막기보다, 감수 항목으로 기록하고 후속 과제로 남긴다.

---

AI 예문 생성 안정화와 관련된 ADR이다. 전체 흐름은 [AI_RESILIENCE_PLAN.md](./AI_RESILIENCE_PLAN.md)를 본다.

### ADR-001: 예문 생성 응답 스트리밍을 보류한다
**결정**: 동기 응답을 유지한다. 대기 문제는 타임아웃 상한(20s), 프론트 로딩 표시, 버튼 비활성화로 해결한다.
**이유**: 응답이 예문 한 문장(max-tokens 300)이라 정상일 때는 원래 빨리 온다. 사용자가 지치는 진짜 원인은 타임아웃이 없어 무한히 기다리는 상황이다. 스트리밍을 하려면 프롬프트 출력 형식(엄격한 JSON → 줄 단위), 새 SSE 엔드포인트, 프론트 수신 방식을 바꿔야 한다(`EventSource`는 `Authorization` 헤더를 못 보내므로 `fetch` 스트림 필요). 또 "스트림이 끝난 뒤 저장·차감" 흐름과 중간에 끊겼을 때의 처리도 새로 설계해야 한다.
**트레이드오프**: Claude 채팅처럼 토큰이 바로바로 보이는 체감 속도를 포기한다. 응답이 길어지는 기능(여러 예문, 설명 등)을 추가할 때 다시 검토한다.

### ADR-002: 예문 생성 API를 GET에서 POST로 바꾼다
**결정**: `GET /api/v2/openai/search`(query) → `POST /api/v2/openai/search`(JSON body)
**이유**: 이 요청은 단어를 저장하고 사용량을 차감하며 외부 과금을 일으키므로 상태를 바꾸는 요청이다. GET은 안전한 메서드로 취급되어 브라우저·프록시의 재전송이나 프리페치 대상이 될 수 있다. 멱등성 키 헤더와 body 검증(`@Valid @RequestBody`)과도 잘 맞는다.
**트레이드오프**: 프론트 호출 코드와 `docs/API.md`를 함께 바꿔야 한다. 브라우저 주소창으로 간단히 테스트할 수 없다.

### ADR-003: 사용량은 선차감하고, 실패하면 환불한다
**결정**: OpenAI 호출 **전에** 기존 조건부 UPDATE(`consumeUsage`)로 차감하고 별도 트랜잭션으로 커밋한다. OpenAI 실패, 응답 파싱 실패, 단어 저장 실패 시에는 +1 환불한다. `possibleUsage` 사전 확인은 없앤다.
**이유**: 기존 "확인 → 호출 → 차감" 순서에서는 잔량 1인 사용자가 동시에 N번 요청하면 N번 모두 OpenAI에 과금됐다. 조건부 UPDATE 하나로 확인과 차감을 원자적으로 처리하면 호출 수가 잔량을 넘지 않는다. 호출 전에 커밋하는 것은 OpenAI를 기다리는 동안 DB 커넥션과 트랜잭션을 잡고 있지 않기 위해서다.
**트레이드오프**:
- 실패하면 사용자는 차감되지 않지만, OpenAI 쪽에서는 이미 과금됐을 수 있다(예: 응답을 받았는데 파싱에 실패한 경우). 사용자 경험을 우선한다.
- 차감과 환불 사이에 서버가 죽으면 사용자는 1회를 잃는다. 확률이 낮아 감수한다.

### ADR-004: OpenAI 에러 분류, 재시도, 20초 상한
**결정**:
- 5xx, 연결 타임아웃, 응답 타임아웃만 최대 1회 재시도한다.
- **429는 rate limit과 insufficient_quota를 구분하지 않고 재시도하지 않는다.** 400·401·403도 재시도하지 않는다.
- 시간 예산은 시도당 연결 2s + 응답 7s, 백오프 1s로, 최악의 경우 19s다.
- **`application.yml` 설정만으로 구현한다.**
  - `spring.ai.retry.max-attempts: 1`, `on-client-errors: false`, `backoff.initial-interval: 1s`
  - `spring.http.clients.connect-timeout: 2s`, `read-timeout: 7s`
- 재시도는 Spring AI 내장 `RetryTemplate` 한 계층에서만 한다.
- 재시도 직전 데드라인 확인은 후속 과제로 미룬다.
- 사용자에게는 공통 바디 `{code, message}`로 응답한다(400 `INVALID_INPUT`, 409 `REQUEST_IN_PROGRESS`, 429 `USAGE_EXHAUSTED`, 503 `AI_UNAVAILABLE`). OpenAI 내부 원인은 숨기고 ERROR 로그로 남긴다.

**이유**:
- **기존 동작이 위험했다.** jar를 확인해 보니 Spring AI 기본값은 최대 10회 재시도, 2s 시작·5배 증가·최대 180s 간격 백오프였고, HTTP 타임아웃은 없었다. 장애가 나면 검색 1회가 수십 분 걸리고 OpenAI 호출이 반복될 수 있었다.
- 일시적인 장애만 재시도해야 비용이 낭비되지 않는다. 429를 구분하려면 에러 본문을 파싱해야 하는데, 트래픽이 작은 서비스라 rate limit에 걸릴 일이 드물다. 그래서 단순함을 택했다.
- Spring AI의 에러 핸들러는 `on-client-errors=false`(기본값)이면 4xx를 `NonTransientAiException`으로 바꿔 재시도하지 않는다. 그래서 429 제외는 설정만으로 된다.
- 시도당 타임아웃만 두면 재시도가 붙었을 때 상한이 깨진다(3s+10s 두 번이면 26s). 그래서 예산 계산으로 상한을 강제한다.
- 데드라인 확인은 `RetryTemplate` 빈을 직접 등록해야 해서 코드와 관리할 거리가 늘어난다. 정적 예산만으로 최악 19s를 지킬 수 있으므로 미룬다.
- 재시도 계층이 겹치면 시도 횟수가 곱해진다.

**트레이드오프**:
- 일시적인 rate limit도 바로 503이 된다.
- 시도당 응답 타임아웃이 7s라, OpenAI가 느린 날에는 실패율이 오를 수 있다.
- 데드라인 확인이 없어서, 앞 단계(검증, Redis, 선차감)가 비정상적으로 느리면 20s를 조금 넘을 수 있다.

**확인 필요**:
- connect 2s는 서버에서 연결 시간을 실측한 뒤 확정한다.
- `RestClient`가 `spring.http.clients.*`를 따르는지, read 타임아웃이 바이트 사이 간격인지 전체 시간인지, `max-attempts`의 정확한 의미(첫 시도 제외 여부)는 로컬 실측과 문서로 확인한다.

**후속 과제**: `RetryTemplate` 빈을 직접 등록해 `RetryPolicy.timeout`으로 데드라인을 확인한다. 자동 설정의 빈은 `@ConditionalOnMissingBean`이라 교체할 수 있다.

### ADR-005: Redis 기반 멱등성 키
**결정**:
- `Idempotency-Key` 헤더는 필수다(없으면 400). 값은 UUID 형식(8-4-4-4-12 hex)만 허용하고, 소문자로 바꿔서 쓴다(형식이 틀리면 400).
- 선차감보다 먼저 Redis `SET idem:<user>:<key> IN_PROGRESS NX EX 30`을 한다.
- 성공하면 응답 JSON과 함께 `DONE`(TTL 24h)으로 바꾸고, 같은 키가 오면 그 응답을 그대로 돌려준다.
- 처리 중에 같은 키가 오면 즉시 409를 돌려준다.
- 실패하면 키를 삭제해 같은 키로 다시 시도할 수 있게 한다.
- 프론트는 사용자 액션마다 새 키를 만들고, 같은 요청을 재시도할 때는 키를 재사용한다.
- **Redis 장애(키 등록 실패) 시 fail-closed**: 차감·OpenAI 호출 전에 503 `TEMPORARILY_UNAVAILABLE`로 막는다.
- **저장된 `DONE` 응답을 복원하지 못하면** 503 `TEMPORARILY_UNAVAILABLE`을 돌려준다. 다시 처리하지 않고 키도 지우지 않는다. 프론트는 이 503을 받으면 새 키로 재시도한다.
- 흐름 조립(멱등성 키 → 선차감 → 호출 → 저장 → `DONE` 기록)은 컨트롤러가 아니라 `search.SearchService`가 맡는다. 이 서비스에는 `@Transactional`을 붙이지 않는다(ADR-003: 차감이 OpenAI 호출 전에 커밋되어야 한다).

**이유**: 선차감은 "한도를 넘는 호출"을 막지만, 네트워크 재전송으로 같은 요청이 두 번 실행되어 두 번 차감·과금되는 것은 막지 못한다. 이미 Redis를 쓰고 있어 TTL로 만료 처리를 공짜로 얻는다. `IN_PROGRESS` TTL(30s)은 요청 상한(20s)보다 길게 둬서, 처리 중에 키가 만료되는 일이 없게 한다. 409로 즉시 응답하면 서버 스레드가 대기하지 않아도 된다.
- fail-closed: 멱등성 없이 진행하면 중복 차감·중복 과금 보호가 사라진다. Redis는 JWT refresh 화이트리스트에도 쓰여, Redis가 죽으면 어차피 서비스 일부가 멈춘다.
- `DONE` 복원 실패 시 재처리 금지: 이미 차감·과금·저장이 끝난 요청이라, 다시 처리하면 중복 과금이 된다. 정상이라면 일어나지 않는 경우라 키 삭제 로직을 따로 두지 않았다.
- UUID 검증: 헤더 값이 Redis 키에 그대로 들어가므로 길이와 문자를 제한한다. 구분자 `:`가 들어올 수 없어 다른 사용자의 키와 겹치지 않는다. `@Pattern` 대신 컨트롤러에서 직접 검사한 이유는, `@RequestHeader`에 제약 어노테이션을 붙이면 메서드 검증이 켜져 body 검증 예외 타입이 바뀔 수 있어서다(문서 확인 필요).
- 서비스 분리: 사용량·AI·단어·Redis 네 곳을 조립하는 로직이라, 컨트롤러에 두면 HTTP 계층이 비대해지고 테스트하기 어렵다.

**트레이드오프**: Redis 장애 동안 예문 검색이 전부 503이 된다. 키의 기록이 24h 뒤에 사라지므로, 그 뒤의 재전송은 새 요청으로 처리된다. `DONE` 값이 깨지면 그 키는 24h 동안 503만 돌려준다.

### ADR-006: 멱등성 키의 감수 항목 (후속 과제)
**결정**: 아래 경우는 이번에 막지 않고 감수한다.
1. **같은 키에 다른 요청 내용**: 요청 내용(keyword, lang, meaning, topic)이 달라도 검사하지 않고, 그 키에 저장된 이전 응답을 돌려준다.
2. **단어 저장은 성공했는데 `DONE` 기록이 실패**(Redis 오류 등): 사용자에게는 200으로 응답한다. 결과가 이미 저장됐으므로 환불하지 않고, WARN 로그를 남긴다. 키는 `IN_PROGRESS`로 남았다가 30s 뒤 만료된다.
3. **키 삭제·`DONE` 기록 시 소유권을 확인하지 않음**: 실패 시 키 삭제(`DEL`)와 성공 시 `DONE` 기록(`SET`)은 그 키를 내 요청이 잡았는지 확인하지 않고 실행한다.

**이유**:
- 1번: 프론트가 액션마다 새 키를 만들기 때문에 다른 내용에 같은 키를 쓸 일이 거의 없다. 학습 프로젝트 규모에서는 단순함을 우선한다.
- 2번: 단어 저장(DB)과 키 기록(Redis)은 한 트랜잭션으로 묶을 수 없다. 이 경우가 생기려면 저장 직후 Redis가 실패해야 하므로 드물다.
- 3번: 문제가 생기려면 처리가 `IN_PROGRESS` TTL(30s)을 넘겨야 하는데, 최악 경로가 19s라 정상 경로에서는 일어나지 않는다.

**트레이드오프 / 영향**:
- 1번: 클라이언트 버그로 키가 재사용되면, 사용자는 요청과 다른 예문을 받는다.
- 2번: 30s 안에 같은 키로 재시도하면 409를 받는다. 30s 뒤에 재시도하면 새 요청으로 처리되어 **중복 차감·중복 과금·중복 단어 저장**이 생긴다.
- 3번: DB 지연 등으로 처리가 30s를 넘기면 키가 만료되고, 같은 키의 다른 요청이 키를 잡을 수 있다. 그 뒤 늦게 끝난 요청이 남의 `IN_PROGRESS`를 지우거나 덮어써서 중복 실행이 생길 수 있다.

**후속 과제**:
- 1번: `DONE` 값에 요청 해시를 함께 저장하고, 해시가 다르면 422를 돌려준다(Stripe 방식).
- 2번: `DONE` 기록을 짧게 재시도한다. 또는 단어 테이블에 멱등성 키 컬럼을 두어, 키가 `IN_PROGRESS`일 때 DB를 조회해 이미 저장된 결과를 돌려주게 한다.
- 3번: `IN_PROGRESS` 값에 요청마다 만든 토큰을 넣고, 삭제·기록할 때 토큰이 같을 때만 실행한다(Lua 스크립트로 비교와 실행을 원자적으로).

#### 변경 이력
**2026-11-24: 감수 항목 3번(소유권 미확인) 추가**
- **바뀐 점**: 1·2번은 그대로 두고 3번을 추가했다.
- **이유**: 구현 리뷰에서 `releaseIdempotency`·`markIdempotencyDone`이 무조건 실행된다는 점이 지적됐다. 정상 경로에서는 일어나지 않아 감수하기로 했다.

### ADR-007: 비동기 처리·폴링과 전체 비용 상한은 이번 범위에서 제외한다
**결정**: 비동기 처리와 폴링, 서비스 전체 비용 상한(OpenAI 대시보드 월 한도 설정, `UsageScheduler`가 Lua 스크립트와 다른 키 `API:usage`를 리셋하는 버그 수정)은 후속 과제로 남긴다.
**이유**: 20초 상한의 동기 호출로 충분하다. 사용자 단위 과금 보호(선차감 + 멱등성 키)를 먼저 끝내는 것이 우선이다.
**트레이드오프**: 전역 한도 버그가 고쳐질 때까지는 사용자별 한도만 실질적으로 동작한다. OpenAI 대시보드 월 한도 설정은 코드 변경이 아니므로 바로 해두는 것을 권장한다.
