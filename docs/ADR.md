# Architecture Decision Records

## 철학
학습 프로젝트 규모에 맞게 **단순한 구현을 우선**한다. 다만 **외부 API 과금 보호는 타협하지 않는다.**
드문 엣지 케이스는 복잡한 장치로 막기보다, 감수 항목으로 기록하고 후속 과제로 남긴다.

---

AI 예문 생성 안정화와 관련된 ADR이다. 전체 흐름은 [AI_RESILIENCE_PLAN.md](./AI_RESILIENCE_PLAN.md)를 본다.

### ADR-001: 예문 생성 응답 스트리밍을 보류한다
**결정**: 동기 응답을 유지한다. 대기 문제는 타임아웃 상한(20s), 프론트 로딩 표시, 버튼 비활성화로 해결한다.
**이유**: 응답이 예문 한 문장(max-tokens 300)이라 정상일 때는 원래 빨리 온다. 사용자가 지치는 진짜 원인은 타임아웃이 없어 무한히 기다리는 상황이다. 스트리밍을 하려면 프롬프트 출력 형식(엄격한 JSON → 줄 단위), 새 SSE 엔드포인트, 프론트 수신 방식을 바꿔야 한다(`EventSource`는 `Authorization` 헤더를 못 보내므로 `fetch` 스트림 필요). 또 "스트림이 끝난 뒤 저장·차감" 흐름과 중간에 끊겼을 때의 처리도 새로 설계해야 한다.
**트레이드오프**: Claude 채팅처럼 토큰이 바로바로 보이는 체감 속도를 포기한다. 응답이 길어지는 기능(여러 예문, 설명 등)을 추가할 때 다시 검토한다.

### ADR-002: 예문 생성 API를 GET에서 POST로 바꾼다
**결정**: `GET /api/v2/openai/search`(query) → `POST /api/v2/openai/search`(JSON body)
**이유**: 이 요청은 단어를 저장하고 사용량을 차감하며 외부 과금을 일으키므로 상태를 바꾸는 요청이다. GET은 안전한 메서드로 취급되어 브라우저·프록시의 재전송이나 프리페치 대상이 될 수 있다. 멱등성 키 헤더와 body 검증(`@Valid @RequestBody`)과도 잘 맞는다.
**트레이드오프**: 프론트 호출 코드와 `docs/API.md`를 함께 바꿔야 한다. 브라우저 주소창으로 간단히 테스트할 수 없다.

### ADR-003: 사용량은 선차감하고, 실패하면 환불한다
**결정**: OpenAI 호출 **전에** 기존 조건부 UPDATE(`consumeUsage`)로 차감하고 별도 트랜잭션으로 커밋한다. OpenAI 실패, 응답 파싱 실패, 단어 저장 실패 시에는 +1 환불한다. `possibleUsage` 사전 확인은 없앤다.
**이유**: 기존 "확인 → 호출 → 차감" 순서에서는 잔량 1인 사용자가 동시에 N번 요청하면 N번 모두 OpenAI에 과금됐다. 조건부 UPDATE 하나로 확인과 차감을 원자적으로 처리하면 호출 수가 잔량을 넘지 않는다. 호출 전에 커밋하는 것은 OpenAI를 기다리는 동안 DB 커넥션과 트랜잭션을 잡고 있지 않기 위해서다.
**트레이드오프**:
- 실패하면 사용자는 차감되지 않지만, OpenAI 쪽에서는 이미 과금됐을 수 있다(예: 응답을 받았는데 파싱에 실패한 경우). 사용자 경험을 우선한다.
- 차감과 환불 사이에 서버가 죽으면 사용자는 1회를 잃는다. 확률이 낮아 감수한다.

### ADR-004: OpenAI 에러 분류, 재시도, 20초 상한
**결정**:
- 5xx·연결 타임아웃·응답 타임아웃만 최대 1회 재시도한다. 429(종류 구분 없음)·400·401·403은 재시도하지 않는다.
- 시간 예산: 시도당 연결 2s + 응답 7s, 백오프 1s → 최악 19s.
- `application.yml` 설정만으로 구현하고, 재시도는 Spring AI 내장 `RetryTemplate` 한 계층에서만 한다.
- 사용자에게는 `{code, message}`로 응답하고, OpenAI 내부 원인은 ERROR 로그로만 남긴다.

**이유**: Spring AI 기본값(최대 10회 재시도, 최대 180s 간격 백오프, 타임아웃 없음)이면 장애 때 검색 1회가 수십 분 걸리고 과금이 반복된다. 429 구분은 본문 파싱이 필요한데 트래픽이 작아 단순함을 택했다. 시도당 타임아웃만으로는 재시도가 붙으면 상한이 깨지므로 예산 식으로 강제한다.
**트레이드오프**: 일시적인 rate limit도 바로 503이 된다. OpenAI가 느린 날에는 실패율이 오를 수 있다. 앞 단계가 비정상적으로 느리면 20s를 조금 넘을 수 있다.
**후속 과제**: `RetryTemplate` 빈을 직접 등록해 재시도 직전 데드라인을 확인한다.
**근거 자료**: [notes/spring-ai-retry.md](./notes/spring-ai-retry.md) (jar로 확인한 기본값, 문서 확인 필요 항목)

**변경 이력**
- 2026-11-21: "재시도 직전 데드라인 확인" → 후속 과제로 미룸. "설정으로 안 되면 직접 구현" → yml 설정만으로 확정. 설정만으로 429 제외까지 되고, 정적 예산으로 19s를 지킬 수 있어서.

### ADR-005: Redis 기반 멱등성 키
**결정**:
- `Idempotency-Key` 헤더(UUID) 필수. 없거나 형식이 틀리면 400.
- 선차감 전에 `SET idem:<user>:<key> IN_PROGRESS NX EX 30`. 성공하면 `DONE:<응답 JSON>`(24h)으로 바꾸고, 같은 키가 오면 그 응답을 돌려준다. 처리 중이면 409, 실패하면 키를 삭제한다.
- Redis 장애 시 fail-closed(503 `TEMPORARILY_UNAVAILABLE`).
- 저장된 응답을 복원하지 못하면 503. 다시 처리하지 않고 키도 남긴다(프론트는 새 키로 재시도).
- 흐름 조립은 `search.SearchService`가 맡고, `@Transactional`을 붙이지 않는다(ADR-003).

**이유**: 선차감은 한도 초과는 막지만 재전송에 의한 중복 차감·과금은 막지 못한다. Redis는 이미 쓰고 있고 TTL로 만료를 공짜로 얻는다. TTL(30s) > 요청 상한(20s)이라 처리 중 만료되지 않는다. Redis 없이 진행하면 과금 보호가 사라지므로 fail-closed로 한다. 헤더 값이 Redis 키에 들어가므로 UUID로 제한한다.
**트레이드오프**: Redis 장애 동안 검색이 전부 503이 된다. 24h가 지난 재전송은 새 요청으로 처리된다. `DONE` 값이 깨지면 그 키는 24h 동안 503이다.

**변경 이력**
- 2026-11-24: Redis 장애 정책 "미결(추천 fail-closed)" → fail-closed 503 확정. UUID 검증, 복원 실패 시 503, `SearchService` 분리를 추가.

### ADR-006: 멱등성 키의 감수 항목
**결정**: 아래 경우는 막지 않고 감수한다.

| # | 경우 | 영향 | 후속 과제 |
|---|---|---|---|
| 1 | 같은 키에 다른 요청 내용 → 이전 응답 반환 | 클라이언트 버그 시 다른 예문을 받음 | `DONE`에 요청 해시 저장, 다르면 422 |
| 2 | 저장 성공 후 `DONE` 기록 실패 → WARN 후 200 | 30s 뒤 같은 키 재시도 시 중복 차감·과금·저장 | `DONE` 기록 재시도, 또는 단어 테이블에 키 컬럼 |
| 3 | 키 삭제·`DONE` 기록 시 소유권 미확인 | 처리가 30s를 넘기면 남의 키를 지우거나 덮어씀 | 요청별 토큰을 넣고 Lua로 비교 후 실행 |

**이유**: 셋 다 정상 경로에서는 드물다(1: 프론트가 액션마다 새 키, 2: 저장 직후 Redis 실패가 필요, 3: 최악 19s < TTL 30s). DB와 Redis는 한 트랜잭션으로 묶을 수 없다.

**변경 이력**
- 2026-11-24: 3번 추가(구현 리뷰에서 지적).

### ADR-007: 비동기 처리·폴링과 전체 비용 상한은 이번 범위에서 제외한다
**결정**: 비동기 처리와 폴링, 서비스 전체 비용 상한(OpenAI 대시보드 월 한도 설정, `UsageScheduler`가 Lua 스크립트와 다른 키 `API:usage`를 리셋하는 버그 수정)은 후속 과제로 남긴다.
**이유**: 20초 상한의 동기 호출로 충분하다. 사용자 단위 과금 보호(선차감 + 멱등성 키)를 먼저 끝내는 것이 우선이다.
**트레이드오프**: 전역 한도 버그가 고쳐질 때까지는 사용자별 한도만 실질적으로 동작한다. OpenAI 대시보드 월 한도 설정은 코드 변경이 아니므로 바로 해두는 것을 권장한다.
